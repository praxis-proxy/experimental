Per-app token budgets, mixed algorithms, shared across gateway replicas

What this demo proves — a scoped MVP slice of ai#658/ai#789, exercised on a two-instance stack.

Gateway A
token_rate_limit: gold-tier (sliding_window) + silver-tier (token_bucket)
↔
Shared Valkey ledger
one budget per x-app-id, per rule
↔
Gateway B
token_rate_limit: gold-tier (sliding_window) + silver-tier (token_bucket)
  1. Per-rule algorithm choice: app-a/app-c match gold-tier (sliding_window); app-b matches silver-tier (token_bucket) — same filter, two algorithms, chosen per rule.
  2. Cross-instance enforcement, both algorithms: app-a's sliding-window budget and app-b's token-bucket budget, each exhausted on Gateway A, are denied on Gateway B too.
  3. Per-app isolation: app-c's budget is untouched by app-a's exhaustion, even under the same algorithm and rule.
  4. Reservation-based admission: each admitted request reserves its estimated cost up front, atomically, via the shared ledger, for either algorithm.
  5. Automatic recovery, two different mechanisms: app-a's budget recovers once its reservation ages out of the sliding window; app-b's recovers as its bucket refills continuously — no manual reset for either.
Scope: two gateway replicas, one Valkey instance, no Grid, no multi-cluster routing, no authentication. See the demo README for what's explicitly out of scope.
